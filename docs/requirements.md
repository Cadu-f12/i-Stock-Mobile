# I-STOCK Mobile — Requirements v6

**Date:** 14/11/2026  
**Version:** v6 — mandatory cutting insert photo capture  
**Scope:** simplified mobile version focused on cutting insert consultation and stock updates.

## 1. Objective

I-STOCK Mobile must support consulting cutting inserts and updating their balances by recording stock entries and withdrawals. The application is not intended to maintain cutting insert master data; that data is consulted through the web system/API.

The application must be offline-first: prioritize local data and retain movements made without a connection for later synchronization, according to the operations accepted by the I-STOCK Manager API.

## 2. Permission matrix

| Area / information | Consult | Add to stock | Remove from stock | Master data / other operations |
|---|---:|---:|---:|---:|
| Cutting insert data (SKU, description, manufacturer, minimum stock) | Yes | Not applicable | Not applicable | No |
| Stock for a specific cutting insert | Yes | Yes | Yes | No |
| Movements and history | Yes | Generated by stock entry | Generated by stock withdrawal | No |
| Users | Yes | No | No | No |
| Manufacturers | Yes | No | No | No |
| Distributors/suppliers | Yes | No | No | No |
| Movement reasons | Yes | No | No | No |
| Cutting insert photo | Yes | Not applicable | Not applicable | Capture and associate a local photo |
| Other I-STOCK Manager information available through the API | Yes | No | No | No |

Each stock entry or withdrawal must generate a movement linked to the selected cutting insert. The user may consult the history, but may not edit or remove movements that have already been recorded.

## 3. Functional requirements

### RF-01 — Consult cutting inserts and stock

The application must allow the user to locate a cutting insert and consult its data, including SKU, technical description, manufacturer, minimum stock, and current balance, when provided by the API or stored locally.

### RF-02 — Consult auxiliary information

Users, manufacturers, suppliers, movement reasons, and other available data may be consulted. The mobile app must not allow users to create, edit, or remove this master data.

### RF-03 — Record a stock entry

The user must be able to add a quantity to the stock of a specific cutting insert. The entry must use the operation accepted by the API and generate a movement with the cutting insert, quantity, responsible user, reason, and date/time.

### RF-04 — Record a stock withdrawal

The user must be able to remove a quantity from the stock of a specific cutting insert. The withdrawal may not exceed the available balance. The withdrawal must use the operation accepted by the API and generate a movement with the cutting insert, quantity, responsible user, reason, and date/time.

### RF-05 — Consult movement history

The application must display recorded entries and withdrawals, including the data provided by the API: type, cutting insert, quantity, reason, responsible user, and date/time. The history is read-only.

### RF-06 — Do not maintain cutting insert master data

The mobile app must treat cutting insert master data as read-only. Creating, editing, or removing a cutting insert remains the responsibility of the web system or other means authorized by the API.

### RF-07 — Photograph the cutting insert label or packaging

The application must allow the device camera to photograph the label or packaging of a cutting insert and associate the image with the corresponding item. The image must be stored locally on the device; local data must store its identifier and file path. The photo must not be sent to the API or synchronized with other devices. Photo capture and consultation must work without a connection. If the file is unavailable or the camera cannot be used, the application must report the situation without blocking consultation of the cutting insert's other data.

## 4. Offline-first requirements and synchronization

### RO-01 — Read local data first

Queries must prioritize SQLite data. Without a connection, the application presents data stored on the device and indicates when it was last updated.

### RO-02 — Record movements offline

If the API and business rules allow the operation offline, entries and withdrawals must be saved locally as pending items for later submission. The interface must distinguish them from movements already confirmed by the API.

### RO-03 — Validate withdrawals

Withdrawal validation must consider the available local balance and pending movements on the device to prevent the user from removing more units than are in stock. The API remains responsible for confirming the movement on the server.

### RO-04 — Synchronize with the API

When the connection returns, the application must send pending movements and update local data with the API responses, respecting its endpoints, formats, and authentication rules.

### RO-05 — Preserve pending items and signal conflicts

Failures or conflicts must not delete pending movements. If the balance or data was changed in the web system before synchronization, the application must retain the local operation, signal the conflict, and must not silently overwrite data.

### RO-06 — Report offline unavailability

If a required datum is not stored on the device, the application must report that it is unavailable offline, without presenting content as if it were up to date.

## 5. Data and relationships

- Cutting insert: identifier, manufacturer, SKU, technical description, minimum stock, and current balance; consulted data, not editable on mobile.
- Movement: identifier, cutting insert, operation type (entry or withdrawal), quantity, responsible user, reason, date/time, and synchronization status.
- Identifiers and relationships must remain compatible with the I-STOCK Manager API.
- Local persistence: SQLite, including required consultation data and pending movements.

## 6. Technology stack

- Mobile application: Flutter.
- Language: Dart.
- HTTP requests to the API: `http` library.
- Application architecture: BLoC (Business Logic Component).
- BLoC implementation: `flutter_bloc` library.
- Local database: SQLite.
- Communication with the backend must follow the existing web API contract.

### Interface states

- Main screens must provide loading, content, empty, and error states.
- The interface must distinguish locally consulted balance, pending movements, confirmed movements, and synchronization failures.

## 7. Local notifications

The application must maintain local notifications to inform the user about movements pending synchronization. They may also be used for low-stock alerts, based on the locally available balance and minimum stock. When data is out of date, the alert must indicate that condition.

The device camera and local notifications are the native resources selected for this version. The timing, frequency, and preferences for each type of alert still need to be defined.

## 8. Local database architecture

The local database will be SQLite. It will store the data required for offline queries, the cached balance, and movements awaiting synchronization. Its structure must remain compatible with the identifiers and data accepted by the I-STOCK Manager API.

### Entities and tables

- **CuttingInsert**: local identifier and API identifier, unique SKU, technical description, manufacturer, minimum stock, and current cached balance. The mobile app consults master data; master data maintenance remains in the web system.
- **User**: identifier, name, and login, to identify the user responsible for each movement. Credential storage is not defined by this model.
- **Manufacturer**: identifier, name, contact, and active/inactive status.
- **Supplier**: identifier, name, contact, and active/inactive status.
- **CuttingInsert_Supplier**: associative table between cutting inserts and suppliers, allowing one cutting insert to have several suppliers and one supplier to supply several cutting inserts.
- **MovementReason**: identifier, description, type (entry or withdrawal), and active/inactive status.
- **Movement**: local identifier and API identifier, cutting insert, responsible user, reason, type, quantity, date/time, and synchronization status.
- **CuttingInsertPhoto**: association between the cutting insert and the path to the image file stored locally on the device. The file is not sent to the API or synchronized.

### Relationships and integrity

- One manufacturer may be associated with several cutting inserts; each cutting insert has one manufacturer.
- Cutting inserts and suppliers have a many-to-many relationship through `CuttingInsert_Supplier`.
- One cutting insert may have several movements; each movement belongs to one cutting insert.
- One user may be responsible for several movements; each movement references one user.
- One reason may be used in several movements; each movement references one reason.
- Foreign keys must preserve relationship integrity.

### Local balance and synchronization

The `Movement` table must distinguish operations pending from operations confirmed by the API. Tables must retain the necessary synchronization metadata, such as the identifier received from the API, pending/synchronized status, and last-update date.

For offline queries, the application uses the most recent cached balance together with local pending movements. Pending entries increase the projected local balance; pending withdrawals reduce it. The server-confirmed balance must be updated according to API responses, without deleting pending operations in case of failure or conflict.

SQLite must not invent a soft-delete rule for cutting inserts. Changes and removals must follow the actual operations and responses of the web API. Historical records must retain their relationships as permitted by the backend.

## 9. Requirements tracking and governance

During development, the agent must consult this document frequently and validate completed implementations against the requirements defined here.

If the agent identifies a new requirement, a gap, or that an existing requirement needs to change to reflect the system, the agent must explain to the user what was found, why the change is necessary, and which implementation or scope areas will be affected. Before modifying this document or treating the change as an approved requirement, the agent must request authorization from the user and wait for their decision.
